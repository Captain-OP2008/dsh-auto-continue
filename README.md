# dsh-auto-continue

DSH 的**自动续行**插件：当某一轮对话**非正常结束**时，替你按下「继续」。

解决的两种典型卡壳：

1. **输出 token 上限**——模型回复写到一半被截断，会话停在那里，需要你手动说一句「继续」；
2. **本轮运行失败**——模型请求失败、步骤抛错，这一轮直接结束，任务半途而废。

插件观察到这类结束原因后，**等该会话回到空闲**，自动排入一条续行指令（同一会话、不新开会话、不改历史），让模型从中断处接着干。

## 触发条件

| `turn/end` 原因 | 默认行为 | 说明 |
|---|---|---|
| `max-tokens` | ✅ 续行 | 输出达到 token 上限被截断 |
| `error` | ✅ 续行 | 本轮请求失败 / 步骤抛错（续行指令里带上错误码与信息） |
| `aborted` | ❌ 不续行 | 中断。**人类按停止永远不续行**；打开 `onAborted` 后仅接管非用户原因的中断 |
| `completed` / `blocked` | ❌ 不续行 | 正常收尾，并把这一段「连续异常」清零 |

## 行为细节

- **等空闲再排队**：`turn/end` 落盘后，插件等 `agent/status → idle` 才调用 `agent.followup(...)`，因此不会与正在收尾的轮次抢时序；排队前会重新校验「同一个 live agent 且空闲」。
- **排队都发生在空闲之后**：连「到顶通知」也走同一条路径，用 `send(..., 'next-turn', false)` 入队（不唤醒）——运行中的轮次绝不会看见它，所以通知**不会自己开出一轮**。
- **用户优先**：一旦出现人类消息（`source.kind === 'user'`），排队中的续行立即作废、连续计数清零——你插话，它就让位。
- **到顶即停**：连续续行达到 `maxContinuations`（默认 3）后停止，并在会话里留一条 notice（`<auto_continue_notice>`），聊天里看得见「自动续行已停止」，随时可以自己接手；同一段连续异常只通知一次。
- **失败先退避**：`error` / `aborted` 类续行按 `retryBackoffMs`（默认 500ms）指数退避（500 → 1000 → 2000，封顶 10 倍），避免模型或网络故障时把 API 打爆；输出截断说明模型工作正常，不退避。
- **子代理默认不管**：只接管顶层会话；`includeSubagents: true` 后才管子代理会话。
- **收手干净**：插件卸载 / agent 被回收时排空进行中的驱动，不再排队。
- **零外部依赖**：只用 node 内置模块与注入的 `agents` 服务，`link:` 装配也能直接跑。

## 连续计数从哪来

「这一段连续异常有多长」**从会话历史推导**：从日志尾部往回数**会被本插件接手的 `turn/end`**，遇到 `completed` / `blocked` 或人类消息即归零。

为什么数 `turn/end` 而不是数自己排入的续行消息：**本轮以 `error` 收场时，步骤在领取消息之前就失败了，续行消息根本不会落进会话日志**。数消息会永远得到 0，从而无限续行（实测复现过：一个不存在的模型让会话在一分钟内空转 2000+ 轮）；数「会被接手的 turn」在两种场景下都成立。

插件内存里另有一份计数兜底（`driven`），与历史值取**较大者**，历史读不到时（极端裁剪、异常重载）仍然会收手。因为读的是持久会话日志，**插件热重载、宿主重启、会话 resume 之后上限依然成立**。

## 配置

在 bundle 的插件行里改 `config`（缺省即用下表默认值）：

```yaml
- insert:
    - id: auto-continue
      name: dsh-auto-continue
      config:
        maxContinuations: 5
        onAborted: true
```

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `enabled` | boolean | `true` | 总开关 |
| `onMaxTokens` | boolean | `true` | 输出上限截断后续行 |
| `onError` | boolean | `true` | 本轮报错后续行 |
| `onAborted` | boolean | `false` | 非用户原因的中断后续行（用户按停止始终不续行） |
| `maxContinuations` | integer ≥ 0 | `3` | 连续自动续行上限（`0` = 只通知不续行） |
| `includeSubagents` | boolean | `false` | 是否也接管子代理会话 |
| `notifyOnLimit` | boolean | `true` | 到顶时是否在会话里留可见通知 |
| `retryBackoffMs` | integer ≥ 0 | `500` | 失败类续行的首次退避毫秒数（`0` = 不退避） |
| `debugLog` | string \| null | `null` | 诊断用：把每次决策追加写入该文件 |

未知键、类型错误的取值会在插件激活时报错（fail fast，不静默降级）。

## 装配与卸载

```powershell
# 装配（免重启；重启后由 profile bundles 正常装回）
dev_install_package { dir = "<插件包绝对路径>", profile = "desktop" }

# 卸载
dev_uninject_plugin { match = "dsh-auto-continue" }
```

## 验证状态

离线状态机测试：`node tests/state-machine.test.mjs`（**18 项全通过**），覆盖两种触发、`error` 连打不落盘时不会无限续行（回归）、退避、计数重置、用户接管、到顶停止与去重通知、`aborted` 策略、开关、子代理、agent 回收、插件重载后计数恢复、卸载、配置校验。

真实会话验证（desktop profile，热装配后跑真模型）：

| 场景 | 结果 |
|---|---|
| `max-tokens`（`maxTokens: 32` 强制截断） | 自动续行 `1/3`、`2/3`、`3/3`，第 4 轮截断后停止；会话日志里三条续行消息来源均为 `auto-continue` |
| 用户插话 | 排队中的第 3 次续行被作废，轮次交还给用户 |
| 到顶通知 | 不唤醒新一轮；下一次轮到该会话时以 `Auto-continue stopped after 3 attempt(s)` 折叠行出现 |
| `error`（指向不存在的模型） | 续行 3 次后停止（修复前会无限空转），退避生效，只发一条通知 |

## 与 goal 驱动器的关系

`@deepseek-ai/dsh-goal-round-driver` 负责 goal 轮次续行，且它**在 `max-tokens` 时自行停用**（设计如此）。本插件不读写 goal 状态，只补上「非正常结束 → 继续」这一环；goal 处于 armed 时，本插件排队的消息会被它的竞争检测看到，不会互相抢轮次。

## 已知限制

- **`error` 场景下插件看不见「人类消息」**：DSH 在步骤失败时不会把已领取的消息落盘，所以这一步的历史里没有人类消息的痕迹。后果是：模型持续故障时，你手动触发的一轮失败也会计入同一段连续异常，于是更早收到「已到顶」而不是又自动重试三次——这是有意的保守取向（宁可早停，不可失控）；一旦有一轮正常完成，计数立即归零。
- 不感知会话回退 / 消息删除；被删掉的续行消息不会补发。
- 到顶通知是「不唤醒」的排队消息：它在下一次轮到该会话时进入上下文。
